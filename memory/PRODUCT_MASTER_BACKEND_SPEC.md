# Slangcart Product Master — Backend Specification

> **Audience:** the `network-pay-1` backend developer.
> **Created:** 01-Jul-2026 by the web frontend agent.
> **Status:** ⏳ Awaiting implementation. Frontend autocomplete + vendor extra
> fields are already wired to the endpoint contract in this doc — they will
> light up automatically the day the backend ships these routes.

## 0. Why

Vendors waste minutes typing brand, specs, images, MRP for products that are
already catalogued a thousand times over. A shared **Product Master** database
gives them a Flipkart-style autocomplete that fills 90% of the form the
moment they select a match. When the product is genuinely new, we look it up
once from a trusted source, normalize it, save it — and the *next* retailer
who searches gets a database hit. Recurring AI/scraping cost per retailer
therefore trends to zero as coverage grows.

Search target: **P95 < 100ms** (achievable with MongoDB text indexes +
LRU cache for top-N queries).

## 1. Collections

### 1.2 `product_master_history`

Every edit / verify / reject / merge writes a row here — full document
snapshot + actor + timestamp. Never deleted. Enables audit + rollback.

### 1.3 `vendor_products` (existing `products` collection — extend)

Vendors already have this — extend the schema with:

| New field | Type | Notes |
|---|---|---|
| `master_id` | str \| null | FK → `product_master.id`. Nullable for legacy items |
| `selling_price` | float | Vendor's own price (may differ from `mrp`) |
| `offer_price` | float \| null | |
| `store_location` | str \| null | |
| `imei_1` | str \| null | 15-digit Luhn-validated |
| `imei_2` | str \| null | |
| `serial_number` | str \| null | |
| `batch_number` | str \| null | |
| `warranty_months_override` | int \| null | Vendor override of manufacturer warranty |
| `condition` | enum | `new` \| `refurbished` \| `used_like_new` \| `used_good` \| `used_fair` |
| `cash_on_delivery` | bool | Default `true` |
| `delivery_available` | bool | Default `true` |

**Rule**: when `master_id` is set, the following fields on the vendor
document are **derived** from the master and must NOT be editable by the
vendor: `name`, `brand`, `category`, `sub_category`, `description`, `specs`,
`images`, `mrp`, `warranty_months`, `dimensions`, `weight_grams`, `colors`.
Admin can override on a per-vendor basis (they already can — leave that
behaviour alone).

## 3. Keyword generation

`_regenerate_keywords(product)` runs on every insert/update and populates
`keywords: list[str]`. Rules:

1. Split `name`, `brand`, `model_number` on whitespace + non-alphanumeric.
2. Add every non-stop-word token, lowercased.
3. Add each 2-word combination (bigram) that starts with a brand or model
   token (`"Samsung Galaxy"`, `"Galaxy Ultra"`).
4. Add category, sub_category, product_type tokens.
5. Add tokens from significant spec fields (`os`, `network`).
6. De-duplicate, keep alphabetical order for deterministic diffs.

Example — input `"Samsung Galaxy S25 Ultra"` + `Android` + `5G` produces:

```
["5g", "android", "galaxy", "galaxy ultra", "mobile", "phone",
 "s25", "samsung", "samsung galaxy", "samsung s25", "ultra"]
```

Add `"mobile"` and `"phone"` synonyms based on category too.

## 4. Indexes (MongoDB)

```python
# product_master
db.product_master.create_index([("keywords", 1)])
db.product_master.create_index([("brand", 1), ("model_number", 1)], unique=False, sparse=True)
db.product_master.create_index([("upc", 1)], unique=True, sparse=True)
db.product_master.create_index([("ean", 1)], unique=True, sparse=True)
db.product_master.create_index([("barcode", 1)], sparse=True)
db.product_master.create_index([("status", 1), ("category", 1)])
# Text index for /search (fallback when exact-keyword miss)
db.product_master.create_index([
    ("name", "text"), ("brand", "text"), ("model_number", "text"),
    ("description", "text"), ("keywords", "text"),
], weights={"keywords": 20, "name": 10, "brand": 8, "model_number": 6, "description": 2})
```

## 5. Endpoints — public / vendor

All require `HTTPBearer` auth unless stated otherwise.

### 5.1 `GET /api/products/master/search`

Query params:

| Param | Default | Notes |
|---|---|---|
| `q` | required | Minimum 2 chars — else return `[]` immediately |
| `limit` | 10 | Max 25 |
| `category` | null | Optional filter |

Response:

```json
[
  {
    "id": "uuid",
    "name": "Samsung Galaxy S25 Ultra",
    "brand": "Samsung",
    "model_number": "SM-S928B",
    "category": "mobile",
    "thumbnail": "https://.../thumb.webp",
    "mrp": 129999,
    "match_kind": "keyword" | "text",
    "score": 87.4
  }
]
```

Algorithm:

1. Lowercase + trim `q`.
2. Try `keywords: {$in: [q, ...bigrams(q)]}` first → up to `limit`, sorted by
   `search_hits desc`. Return if any matches.
3. Fall back to `$text: {$search: q}` sorted by `{score: {$meta: "textScore"}}`.
4. Only `status: "verified"` documents are returned to non-admins.
5. Wrap the whole handler in an in-process LRU cache keyed by `(q, limit,
   category)` with 60s TTL to blunt keystroke bursts.

**Latency target**: P95 < 100ms on a warm cache, < 250ms cold.

### 5.2 `GET /api/products/master/{id}`

Full product master record (all fields). Non-admins see `verified` only.

### 5.3 `POST /api/products/master/lookup`

Body: `{ name?, upc?, ean?, barcode? }`

Search order:

1. `upc`/`ean`/`barcode` exact match.
2. `keywords`+`text` search (as in 5.1) with `limit=1` and score > threshold.
3. If nothing → external source pipeline (§6). Save result → return.
4. If external also fails → 404 with `{ detail: "not_found" }`.

Response: the newly-created or found `product_master` document, `status:
pending` for freshly-scraped items (awaits admin verification).

### 5.4 `POST /api/products/master/{id}/hit`

Increments `search_hits` — called by frontend when a user *selects* an
autocomplete suggestion. Lets us learn which items to cache aggressively.

## 6. External-source pipeline

For products not yet in the master, we scrape ONCE and cache. Recommended
order (fastest / cheapest first):

1. **UPC/EAN/GTIN databases** — free, structured. e.g. `upcitemdb.com`,
   `openfoodfacts.org` (for FMCG).
2. **Amazon PA-API** if the seller has an affiliate account.
3. **Flipkart affiliate API** if available.
4. **Serpapi / DuckDuckGo scrape** — last resort, needs image + spec parsing.
5. **LLM normaliser** — feed the raw HTML + a JSON-schema prompt to an LLM
   (use the Emergent LLM key playbook) that returns the canonical
   `product_master` shape. Only used when structured sources fail.

Every scrape/normalise call **must**:

- Set `source` + `source_url` on the saved document.
- Set `status = "pending"` (never auto-verify scraped content).
- Rate-limit and dedupe: track outstanding lookups so two vendors typing the
  same product at the same time don't hit the source twice.
- Log the raw source response into a `product_master_scrape_log` collection
  for audit.
- Never save a product with 0 images OR missing brand — refuse instead.

## 7. Image pipeline

On save, every image url in the incoming payload is:

1. Downloaded to a temp buffer.
2. Compared to existing image hashes on the product to skip duplicates.
3. Resized into three variants: `main` (1200×1200 max), `thumb` (240×240),
   `webp` (WebP quality 82 of main).
4. Uploaded to the object-storage bucket (use the storage playbook that's
   already integrated).
5. Sizes + hash + url stored on `product_master.images[]`.

Compression must be async — the endpoint returns as soon as the master is
saved with the original URLs; the pipeline replaces them within a few
seconds. Frontend already renders whichever URL comes back.

## 8. Endpoints — admin

Same collections, `role: admin` required. `product_master_history` written
on every write.

```
GET    /api/admin/product-master                ?q&status&brand&category&limit&offset
GET    /api/admin/product-master/{id}           full doc + history
POST   /api/admin/product-master                create new (defaults to verified)
PATCH  /api/admin/product-master/{id}           partial update; bumps version
POST   /api/admin/product-master/{id}/verify    status→verified; verified_at/by
POST   /api/admin/product-master/{id}/reject    { reason } → status→rejected
POST   /api/admin/product-master/{id}/merge     { target_id } — merges INTO target; migrates all vendor_products.master_id refs
DELETE /api/admin/product-master/{id}           soft-delete: set status=rejected, keep row
POST   /api/admin/product-master/import         multipart CSV / Excel; validates + inserts pending rows
GET    /api/admin/product-master/export         streams CSV
GET    /api/admin/product-master/duplicates     admin dashboard: list clusters by (brand, model_number)
```

### 7.1 Duplicate detection (before insert)

The admin panel calls `POST /api/admin/product-master/duplicates/check` with
a candidate document. Server returns `duplicates: [{id, similarity_score,
reason}]` where reason is one of `same_upc`, `same_brand_model`,
`same_name_within_brand`. Only merge if admin confirms.

## 9. IMEI validation

- 15 digits, Luhn checksum. Utility: `luhn_valid(imei_str) -> bool`.
- Enforced unique globally in `vendor_products.imei_1` and `.imei_2`
  (partial index).
- On POST/PATCH of a vendor product, if IMEI already exists, return 409 with
  `{ detail: "imei_already_registered", by_vendor_id: "…" }`.

## 10. Barcode / QR endpoints

```
POST /api/products/master/scan       body: { code, kind: "upc"|"ean"|"qr"|"barcode" }
```

Same as `POST /lookup` but takes precedence on exact `code` match. If found,
returns the master. Otherwise falls back to the lookup pipeline. Frontend
opens the product directly on success.

## 11. Security / audit

- All admin writes go through `product_master_history` (immutable append).
- `PATCH` requires If-Match header with current `version` to reject
  concurrent overwrites (return 409).
- Sanitize all incoming string fields (strip control chars, cap length at
  reasonable maxes — name: 200, description: 20000).
- Reject unknown MIME types on image URLs.
- Log every failed scrape / duplicate reject / merge with actor id.

## 12. Frontend contract (already implemented)

The web frontend is already wired to this contract. Specifically:

- Vendor "Add product" modal debounces (300ms) the input into
  `/api/products/master/search`. If the endpoint 404s or returns [] the form
  falls back to manual entry — no user-visible error.
- On suggestion select, the frontend calls `/api/products/master/{id}` for
  the full record, populates the form (name, brand, category, description,
  image, MRP, warranty). The vendor then only enters selling_price / stock /
  IMEI / serial / batch / condition / COD / notes.
- On save, the frontend sends `master_id` alongside vendor-specific fields
  to `POST /api/vendor/me/products`.
- The frontend calls `POST /api/products/master/{id}/hit` on selection so
  the backend can prioritise its cache.

## 13. Migration plan

1. Ship §1–§5 endpoints (Product Master + public search) with a small seed
   set of ~200 popular Indian retail SKUs so the autocomplete has something
   to hit on day 1.
2. Add the image pipeline (§7) and external-source fallback (§6). Keep the
   external fallback behind an admin feature flag until the normaliser is
   tuned.
3. Enable admin verification (§8) and import CSV.
4. Enable IMEI + barcode (§9, §10).
5. Add cache warming background job that pre-computes top-10 keyword
   permutations for each of the top-1000 products.
